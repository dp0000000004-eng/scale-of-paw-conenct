Study notes page: how far this design scales

Current path: one JSON GET for a branch, then every link.study_notes item becomes a card in the browser. There is no pagination or virtual list. Graphs are modeled from that architecture, not from a load test.

Campus size is well inside the green zone A polytechnic catalog of Drive folders (about 6 semesters × a handful of folders per branch) stays under ~50 items. Listing every PDF in those folders (~100–250 per branch) is still fine. The current page only becomes the bottleneck if you flatten a whole Drive tree into this JSON.

If you stay with folders (recommended)

Keep study_notes as a few Drive folders per semester, the way the live record already does. Then this graph stays flat: payload stays under a few kilobytes and first paint stays under ~100 ms even if you add every department.

If you list every file

Split the catalog: paginate the JSON, or virtualize the card grid, and stop stuffing the whole Drive listing into one JSONField. That is the line where this page stops being a campus library and starts being a file browser.

Bottom line

For PawConnect as a campus notes library, this page already scales to the whole polytechnic. It does not scale to “every file Google Drive knows about” without pagination.
