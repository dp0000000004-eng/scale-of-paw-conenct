PawConnect scalability on our own server

How many people one self-hosted PawConnect server can serve, and what limits it first. We assume one machine of our own running Nginx, Gunicorn, Django and PostgreSQL. Every number below is modeled from the assumptions in the first table. None of it comes from a load test, and the Paw AI limits depend on a typical AI call time that you should measure on the real system.

The limit is the AI wait, not the page loads A normal page takes a worker a few tens of milliseconds. A Paw AI question holds a worker for the whole wait on the outside AI service, several seconds. So the number of students asking Paw AI at the same moment, not the number of people browsing, is the first thing to run out.

Assumptions behind every number

Change these in the script at the bottom of the page and every table and graph here updates.

1. People browsing at the same time

Modeled from the page time and CPU target in the assumptions. Units: server size on X, people active at the same moment on Y.

2. People using Paw AI at the same time

Each question blocks one Gunicorn worker until the AI answers. Threads let one worker wait on several answers at once. Units: server size on X, students asking Paw AI at the same moment on Y.

3. Page response time as load grows

Simple queue model: response time = page time ÷ (1 − CPU use). Lines that hit the top are saturated, meaning requests queue up and the real wait keeps growing. Units: requests per second on X, milliseconds on Y.

4. Database growth

Paw AI history is the main thing that grows. Units: enrolled students on X, megabytes of new data in one semester on Y.

The real risk of our own server

Capacity is not the weak point. One machine is. Power cuts, a dead internet line or a failed disk take the whole site down, and there is no second server to take over.

Plan for three things: a UPS or a stable power supply, a daily PostgreSQL backup copied to another place (pg_dump), and a short note on how to bring the site back on a new machine.
